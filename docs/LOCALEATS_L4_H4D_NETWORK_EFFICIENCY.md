Date: 2026-11-25. Status: candidate; acceptance pending. R0 additional services; no deployment or hosted changes.

Customer first-card public baseline/full-batch/priority 20/253/16ms, GPS 17/253/16ms, full 252/253/251ms, HTTP 5/2/3. Synthetic delayed-response fixture, not mobile/network proof. ## Exact polling audit
Customer App history effect reads authenticated recent orders and ready notifications every 30s while visible/online; focus, reconnect, push, screen entry and manual reconciliation retained. Catalog 60s while visible/online, nearby alert and cache semantics unchanged. Merchant order inbox polls 15s even with no visible orders because a new order can arrive without FCM. Shop ownership verification every 30s is a security boundary; retain both. Merchant version metadata was polled every 30s, unrelated to order admission.
## Decision
Customer verified idle only: successful owned list with <50 rows and all terminal statuses, outside order-history, order-tracking, checkout/cart; 120s interval instead of 30s. Unknown, active, full/truncated list, ownership mismatch or failure returns to 30s. Existing triggers remain; no inferred order state from push. Merchant version metadata 300s visible/online, no change to order/ownership reconciliation. Proposed scheduled idle Customer history+inbox 240→60/hr (-75%); Merchant metadata 120→12/hr (-90%). These are interval-derived targets, not overall traffic reductions or actual device measurements. Do not claim 50% of all requests or live costs. Need real-user/network measurement, catalog traffic assessment and actual FCM acceptance.
Read-only client cooldown: parse Retry-After delta seconds or HTTP date on 429 and 503 with explicit header, fallback 60s for missing/invalid 429, separate bounded static read scopes, in-memory only, never shorten a deadline, no automatic retries or writes. Customer transport GET scopes catalog/orders/notifications; Merchant actual MerchantApi orders/shop. API already exposes Retry-After in CORS. Existing merchant failed ownership path remains fail-closed. No durable cross-tab quota claim. No automatic write retry or modifications to push, authorization, UI, database, service worker, or server limits.
## Acceptance
Candidate-pinned ten-job workflow, new policy/transport tests, prior first-card regression, disposable database and rules security. Report measured test output separately from theoretical cadence. Verify active order reconciliation and push event hooks, account switch, timeouts, cooldown behavior and actual browser/device later. Retain ALL earlier release blockers including real authenticated navigation, mobile/FCM delivery, PWA update/transfer, Customer first paint target, index rollout locks/write overhead and publication snapshot race. No merge/deployment or hosted DDL. H4E only after H4D accepted.
