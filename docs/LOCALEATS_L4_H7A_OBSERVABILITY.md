## Signal contract (proposal, not live)
Use bounded in-memory aggregate counters/histograms, fixed route-template and result enum, component and coarse environment only; no raw URLs, query strings, IP, GPS, names, email, auth headers, cookies, token, payloads, customer/shop/order IDs, raw exception text, stack, provider body or database SQL parameters. Never log arbitrary labels or stringify objects. Allowlist typed fields; missing/stale/invalid metrics unknown, not zero. Default no export; future sink requires access, retention/deletion and cost review. Aggregate minute windows per warm process, do not average percentiles or combine instance counters as if single process. Include sample count, window and source freshness; low volume use absolute integrity/overdue alerts, not a confident percentile. Avoid metrics endpoint exposure, added protected reads, polling/claim changes, repeated provider probes or synchronous logging in critical path. Bound storage/cardinality and processing; dropped telemetry explicitly counted, no effect on order semantics. Before runtime change audit current log paths and redact at source. No sensitive logs even when debug enabled.

## Candidate indicators and decision triggers
- Admission: existing per-process 600 auth /1200 total per minute caps; review 420/840 (70%), priority 480/960 (80%), cap reached critical operational pressure. Track offered/admitted/denied and unexpected 429, positive Retry-After separately; do not raise caps or retry mutations. Do not infer aggregate fleet capacity from per-process windows.
- API: request count, 5xx, fixed duration histogram by route family; provisional review 1% errors or p95 >=1000ms, priority >=5% errors; percentile interpretation requires >=20 requests per window; use repeated windows and route baseline before incident escalation. These proposed hosted review thresholds are not H4/H6 lab acceptance thresholds. Existing earlier performance misses remain open.
- Database: actual configured connection/pool utilization and wait p95, connection failures, observed lock wait and timeout counts. Review >=70% utilization or wait p95 >=100ms, priority at full pool or wait p95 >=500ms; do not change pool size from H6C process-launch measurements. If provider cannot expose actual pool limits/metrics, unknown. Distinguish SQL execution from queue/network latency.
- Orders: overdue pending, unresolved unknown mutation receipts, lease overdue, invariant violations. Count against existing authoritative deadlines and lease fences, not a new timer or transition. Any integrity violation critical; overdue/unknown priority human reconciliation, no automatic replay or payment changes.
- Notifications: oldest eligible outbox age relative to existing retry/lease schedule, attempts, claims, provider accepted, device observed and inbox reconciliation separately. Overdue eligible job priority; provider acceptance never device delivery. No empty-claim suppression, no extra drain, no new device probes.
- Quotas: per-provider current usage, limit, units, period/reset, source date; review >=70%, priority >=90% or forecast exhaustion within 7 days; unknown if quota/usage stale or inaccessible. Track Firebase, Supabase, Cloudflare/Vercel and GitHub Actions separately, verify current plan/project usage read-only before recommendation. No paid resource authorized. Forecast only with comparable daily samples, no fabricated live quotas. Upgrade recommendation needs observed repeated pressure, root cause, cheaper correction, estimated incremental cost and owner approval.

## Incident runbook (proposal)
P0 integrity/security: stop pilot expansion, preserve sanitized evidence, inspect authoritative records with approved access, never replay uncertain mutations; owner approval for production containment/rollback. P1 overdue order/outbox, capacity/5xx: inspect existing receipt/lease/recovery, classify provider vs app vs DB, avoid retry storms and monitor recovery. P2 repeated quota/latency warning: trend over 3 comparable windows, check data age and deployment version, propose R0 correction first. Escalate any immediate order-integrity issue regardless of volume. Incident record: UTC window, environment, component, severity, aggregate count, evidence reference, action owner, safe rollback, verification; no personal identifiers. Clear alert only after independent recovery evidence; missing data remains unknown. Proposed dedup/cooldown and escalation windows must be rehearsed before deployment. No autonomous production actions.
