Shared auth limit is per warm process not global deployment capacity. No paid tier purchase recommended from fixture alone.

### Demand model and review triggers (not measured traffic or purchase recommendation)
Foreground pool 5/20/100/500, active/unknown20%, verified idle80%, 1 foreground merchant per shop. Two Customer protected reads per cycle (30s active/120s idle), merchant 15s orders and30s shop. Baseline polling 14/62/310/1400 protected requests/minute =2.3/10.3/51.7/233.3% of 600 auth attempts per warm process; formula 1.6*foreground+6*shops for exact 20% mix, excluding push wakes, extra requests and writes. 100 shops alone 600 modeled reads/minute, no headroom at single-process cap; Stage4 exceeds both caps without other traffic. 20/60/160/400 modeled one-device-per-side push opportunities for 10/30/80/200 journeys, not per-minute rate or delivered notifications. No real provider quota tests. Catalog visit illustrative 2 HTTP/3 repo calls for one shop, 3 HTTP/5 repo calls for multiple incl priority plus batch (deferred <=4 repo-call target remains).
Provisional investigation triggers: sustained 70% auth budget (420/min per warm process) or total budget (840/min), or unexpected 429 on normal workload, review measured traffic/active sessions and legitimate admission design; at 80% (480/960) prioritize review before expanding cohort. Never raise/bypass limits blindly. At 25-shop scenario polling310/min before other traffic: instrument/monitor before expansion; 100-shop scenario requires deliberate architecture/admission validation, not immediately paid upgrade. For repeat identical loopback fixture, proposed normal-stage p95<=20ms, p99<=60ms, zero unexpected 429/5xx and integrity zero duplicates; not hosted SLA. DB proposed repeat 10-client p95<=100ms, 20-client p95<=150ms diagnostic guard (observed148.418 near limit), test fixed dataset varying concurrency and longer mixed independent transactions before optimization. Aim repeatability with three samples and sustained load safely within bounded lab, report CPU, peak memory, lock duration and query buffers rather than claim actual capacity. Memory investigation if reproducible growth under equal repeated workload/no recovery, not based on one sequential RSS curve. Upgrade decision needs actual hosted usage, measured quotas, latency/CPU/DB connections/storage and pricing at time of decision; none verified here. R0 incremental paid services. H6A isolated baseline accepted, H6B recommended on explicit approval to refine sustained workload and investigate admission/polling bottleneck before runtime change. All previous health/catalog/auth performance flags, H4E deferred targets, backup/hosted/device/real pickup and other release blockers remain. No production load, hosted writes, merge or intentional deploy.
