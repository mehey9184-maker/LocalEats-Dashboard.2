## Design (bounded proposed workload)
Stages shops/registered synthetic customer identities/foreground actor pool/API concurrency/HTTP requests/DB journeys:
1/25/5/2/100/10; 5/100/20/5/200/30; 25/500/100/10/400/80; 100/2500/500/20/800/200. Population is not concurrent load, no real Firebase accounts. Stage 4 separate 1300 protected HTTP attempts, concurrency20, fresh per-process admission budgets. Actual compiled catalog routes, auth middleware with revoked-check asserted, in-memory repository and synthetic verifier; actual default all1200/auth600 per60s, actor category limits, no bypass. HTTP mixed 1/4 list, menu, up-to-six menu batch, protected fixture; fixture not actual orders/inbox endpoint, no real Supabase/PostgREST/FCM latency. Record p50/p95/p99/max, elapsed, throughput/goodput, status/Retry-After, repository call counts, response bytes, RSS sampled peak, heap and event loop delay. Fixed batches are closed-loop finite samples, no production SLA or stress-until-crash.
DB actual recovered SQL on isolated PG17 minimal fabricated legacy schema, unchanged H2D1 geographic review draft and H5E lease/commit/races first. 20 menu items per shop; cumulative shops/history plus existing small integrity fixtures, stage-specific registered identities and active device tokens. pgbench 2/5/10/20 simultaneous connections, exact 10/30/80/200 committed atomic full journeys (create/accept/ready/payment/collect + exact create/payment/collect replay) with actual functions, assert one order, one payment/collection, five events, one outbox per journey. One atomic transaction for throughput, not real separate HTTP calls or six-month volume; inherited independent transactions and observed-lock races still run. No provider sends. Actual query EXPLAIN ANALYZE BUFFERS for minimal schema history, shop inbox, menu, catalog; no production query/index equivalence. Sample pg_stat_activity lock waits, database memory snapshot, pgbench latency/throughput. Short sample cannot prove saturation boundary or absence of waits. No real database crash or restored hosted backup.
Demand model: 20% foreground active/unknown, remainder verified idle; actual Customer 30/120s two reads (history and notifications) per tick, Merchant15s order and30s shop reads. Model excludes wakes, retries, additional protected reads/quotes/writes and push device management; assumes one foreground merchant per shop and one device each per order; 2 push opportunities/journey, not actual delivery. Catalog visit illustrative list + priority menu + up-to-six bounded batch (single shop 2 HTTP/3 repository calls, multi-shop 3/5); actual mock router measurements separate; no mounted Customer catalog waterfall. Shared auth limit is per warm process not global deployment capacity. No paid tier purchase recommended from fixture alone.
