## Exact source audit
Customer src/services/customerPickup.ts uses approvedShops and per-shop menu for both GPS and public browse; src/services/nearbyCatalogCache.ts and publicBrowseCatalog.ts retain six-worker progressive loading, complete-only 15s memory cache, independent deadlines, no fabricated prices/distances. The retained useShopsData hook is not the authoritative path. API localeats-api/src/routes/catalog.ts lists approved nonarchived shops, applies pilot IDs, and separately verifies every shop before menu read. For N valid returned shops, N+1 HTTP requests and 2N+1 repository operations, excluding retries. Four-shop target <=3 requests. Source count is not hosted query telemetry.
Orders route uses user_id equality, created_at DESC/id DESC for recent and collection-history; history uses keyset cursor and limit 51. Menu read uses shop_id equality. H4A synthetic 25k orders and 10k menu rows scanned 25000 and 10000 respectively. Candidate general B-tree (user_id,created_at DESC,id DESC) covers both recent and history; menu_items(shop_id) supports single and grouped queries. Collection-heavy synthetic fixture is not proof for mixed live workloads; evaluate selectivity, write overhead and deployment locks before any migration. Merchant recent and notifications already have targeted index shapes; no speculative index additions.
## Decision
Keep original endpoints, UI, availability and order admission; add GET /api/v1/catalog/menus?ids=... (1–6 distinct validated IDs). Pilot allowlist before queries, explicit fields, approval and archive predicate, then grouped menu query with exact count and max 500 rows. No unrequested or nonpublic menu allowed, valid empty menu distinguished from missing publication. Any count mismatch fails closed with 413. Customer coalesces concurrent menu calls in microtask, no coordinates/auth included, preserves caller cancellation. Compatibility fallback only for 404/405 or explicit oversized code; no fan-out on 429, network, malformed or 5xx response. Older API fallback increases calls until compatible rollout; no claim of savings for fallback. Existing no-store middleware stays. No auth or permissions change. Separate snapshot publication/menu checks have the same race class as existing endpoint; re-evaluate atomicity before launch. Batch max and row cap are proposed pilot guardrails; larger catalogs need bounded pagination strategy, not unlimited request fan-out.
