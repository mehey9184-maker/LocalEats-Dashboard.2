## Remaining target investigation and decision
1. Customer FCP misses by 188ms (32.6% over 576ms target). Exact index.html already contains inline styled startup skeleton and textual status before entry module. Existing benchmark only records FCP, root children and load; it cannot identify which element painted or prove React usable timing because shell children exist before React. Do not remove skeleton, weaken render checks, change throttle, or manufacture earlier paint. Next focused diagnostic should trace HTML/CSS request timings, startup-shell appearance/removal, actual React mount/usable controls, layout shift and long tasks on same profile; preserve all original UI/permissions. Actual causal bottleneck not proven.
2. Total JS+CSS gzip9 from standard root builds Customer 764076 B (target <=570000 stretch), Merchant 1007643 B (<=750000 stretch). Initial reduction is not total transfer reduction. Separate graph-instrumented build asset totals differ (765969 / 1012714 B); do not mix compression methods/builds. Exact graph candidate Customer eager rendered application 950144 bytes, React DOM 561127, auth 290414, motion-dom 287158; deferred Firestore chunk ~170108 gzip bytes; Merchant eager Firestore 801928 rendered bytes, Leaflet 462123, framer-motion 338324; Marketing chunk 152959 gzip, DashboardOverview 112750, MenuManagement 81018. Graph rendered lengths are not transfer. Audit actual optional/active consumers (especially Merchant Firestore), PWA precache and chunk recovery before removing any dependency or feature; lazy boundaries alone do not reduce total bundle. Stretch misses remain open, not silently waived.
3. Four-shop path actual HTTP 3 PASS. Exact repository source: listing 1, priority single menu public approval check + menu 2, remainder batch public approval subset + menus 2 = 5 read calls in successful ordinary path (target <=4 FAIL). Do not skip current publication checks or use stale/client-approved IDs. Candidate future single-statement bounded server-authoritative read using validated schema relationships or narrowly reviewed SQL read function could combine approval and menu while retaining zero-item/closed/publication/pilot allowlist, limits and field allowlist. Need test isolation and result parity, no hosted DDL; avoid claiming one repository call equals one physical SQL operation, exact-count query can add work. No implementation authorized here beyond review.
## Acceptance decision
H4E evidence/regression accepted, all eleven jobs green; full H4A target acceptance NOT granted (Customer FCP, repository fanout, both stretch totals unmet). Hold L4-H5 until explicit acceptance of a documented tradeoff or targeted remediation and repeat acceptance. Do not conflate stretch misses with release permission. No runtime changes, new deps, merges, hosted migrations or deployment requested/performed. No new paid services. All prior release blockers remain, including live mobile/auth/push/installed PWA, index rollout locking/write cost, backups/security and actual pickup. Proposed next H4E.1 focused measurement-only bottleneck diagnostic and safe catalog-query rehearsal; maintain R0 and original UI.
