## ADR-017 — revocation checked identity on protected API
Observed in exact accepted source: normal Firebase middleware calls verifyIdToken(token) while admin uses verifyIdToken(token,true). Pickup create, history, merchant commands and notification routes use normal middleware. Prior historical claims of revocation hardening do not establish this candidate has it. Require verifyIdToken(token,true) for normal authenticated routes, reject blank/whitespace bearer before provider and log a fixed denial message rather than raw provider errors. No auth cache or fail-open fallback; public catalog is unchanged. Synthetic mounted test covers revoked/disabled tokens across quote, create, history/list, merchant payment, inbox and subscription; no DB reads/RPC before denial. Existing auth/ownership/write gates retained. Verification pending; real Firebase revoked/disabled test and request latency/quota measurements remain separate. Per-request revocation checking adds a provider lookup; monitor Firebase usage, availability and latency rather than disabling security to save cost. ## Read-only hosted public schema exposure (no business rows read)
Catalog-only metadata review: 20 ordinary public tables plus spatial_ref_sys (21 tables total), four views. All application tables RLS enabled; spatial_ref_sys lacks RLS. Only four public SELECT policies, all unconditional: announcements, menu_items, reviews, shops. Orders, profiles, app_error_logs and app_errors have broad raw grants but no policies, so grants alone are NOT proven browser access. Private chat, payments, pickup events/outbox/subscriptions and rider notification tables have no browser table read/write grants and no permissive policies. Both application views shops_with_availability and rider_status_view are security_invoker and deny browser access. Four application SECURITY DEFINER functions inspected (handle_new_user, two nudge_rider variants, rls_auto_enable) have no anon/authenticated execute; three PostGIS st_estimatedextent overloads remain publicly executable, separate extension review. Spatial metadata extension privileges require separate review, not blind revocation.
Confirmed public direct-read boundary gap: shops SELECT true plus column grants exposes owner_id, approval_reason, approval_status, cash-trust flags and other internal columns; pending/archived row filtering absent in DB policy. reviews SELECT true exposes order_id. menu_items and announcements SELECT true do not filter approval/publication/active. API catalog explicitly selects narrower fields and approved/nonarchived rows plus optional pilot allowlist, which direct Data API read policies bypass. No real values or records retrieved. Treat as release blocker for API-only target; actual raw Data API network availability and dependency/legacy consumer compatibility still need review. Do not change production grants here.
