## Architecture boundaries and authority
Prefer a modular monolith, not microservices: Customer/Merchant React PWAs -> central versioned Express API at localeats-api/src/server.ts -> use-case services/contracts -> narrow database repository/RPC -> PostgreSQL. Firebase verifies identity and sends notifications; its acceptance of a push is not delivery or order truth. Cloudflare hosting/R2 migration is an intended direction, not implemented by this review. Merchant API currently contains Vercel config; Customer root server.ts and functions/src/index.ts are separate historical/alternate execution surfaces, not proof of active hosting. All protected business reads/writes should use authorized API; no frontend service-role credentials. Public browsing may show closed and distant shops; checkout admission is independent. Preserve approved UI, pickup-only controlled shop/UID gate, pay at shop, no delivery/rider/LocalPay activation.

## Request path
server.ts: no-store for /api/v1 and disabled ETag -> origin check/CORS -> previewReadOnlyGate -> legacyOrderGuard -> pickupWriteGate -> express.json -> routers -> generic 404/500. CORS is not authorization (non-browser callers exist). Preview gate recognizes VERCEL_ENV=preview or LOCALEATS_PREVIEW_READ_ONLY=true; blocks mutation verbs and GET/HEAD notifications. This is not equivalent to isolated credentials. Production write gate only selected pickup paths; handler checks matter. Do not infer global read-only from PICKUP_WRITES_ENABLED=false.

## Pickup transaction trace
1. Customer src/services/customerPickup.ts uses Firebase registered currentUser and explicit HTTPS production API origin; UI flag and quote can_submit guide UX, not security boundary. Session intent scoped to UID, retries require original consent.
2. routes/orders.ts POST /quote -> parsePickupInput (pickup-v1, exact allowed fields, finite bounded GPS, cash/card_machine, collection only) -> pickupPricing (repository shop availability, 4 km raw distance, authoritative menu price) -> pickupQuote integer minor units and SHA fingerprint. can_submit checks nonanonymous + configured single shop/UID.
3. POST / -> auth -> pickup flag -> controlledPickup -> createPickup. Existing idempotency key replay is checked before current catalog/pricing, hash binds UID and original intent. Fresh request repriced, consent verified then pickup_create_order RPC. SQL drafts include locked-row recheck; deployed RPC/constraints/permissions not verified by this source review. Successful persisted result then best-effort merchant push; replay not resent.
4. Merchant owner/order lookup -> controlled pickup gate -> commandPickup validates UUID command ID, expected revision, reason/payment/handover fields -> pickup_order_command RPC. Receipt validates event/order identity and revision. Customer cancel checks ownership and same pickup contract. Actual payment is at shop, collection explicitly confirmed. Legacy nonpickup cancel/accept/ready branches use direct updates; do not delete without scoped regression.
5. Ready customer push uses pickup_claim_push, pickup_push_sendable, pickup_finish_push with attempt/lease fencing; one awaited attempt per relevant request. Merchant creation push sends best-effort to at most five active devices; no durable retry shown in that function. No timer/cron in drainPickupPush. Notification GET also drains; Preview blocks it. Authoritative inbox remains source of truth.
6. Merchant inbox verifies owner shop IDs; recent 250 and separately paged unfinished rows (250/page, cap 1000 + sentinel); merges/deduplicates, rejects foreign shop or unsafe partial data. Offset paging across concurrent mutations may miss rows; investigate using transaction snapshot/keyset and load tests, not remove safety caps.

## ADR-012 — modular backend, explicit capability gates (proposed)
Keep the central API modular and independently deployable; separate transport, identity, domain/use cases, persistence and asynchronous notification responsibilities. Prefer explicit route capability policy and fail-closed tests before large refactors; keep SQL atomicity, idempotency and revision checks. Do not introduce queues/microservices/native code or paid plans without measured need. Preserve deferred source but prevent unauthorized execution; distinguish read-only catalog/quote, onboarding, controlled pickup, admin and deferred delivery. Source-only next H2B: build complete route/permission test matrix and verify disabled paths using injected mocks with zero DB/RPC/FCM calls; propose narrowly scoped gate changes in separate draft only after reviewing required merchant/admin workflows. H2C frontend/backend access boundary, H2D authoritative contract vectors, H2E combined acceptance. H3–H8 remain separate.
H1E hosted 402 and external backup/physical device acceptance remain unresolved. No live service calls, no secrets accessed, no main merge, no SQL/migration, no flag changes, no deployment or purchase. Rollback for documentation: revert doc commit; runtime untouched.
