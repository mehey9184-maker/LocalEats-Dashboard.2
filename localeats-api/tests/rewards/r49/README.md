## What was tested against actual code

- API source: `localeats-api/src/middleware/authenticateFirebase.ts` uses the R4.8 **draft** `verifyIdToken(token,true)`; `src/routes/orders.ts` provides real mounted Customer GET orders, GET by ID and Merchant order-action handlers. This test uses real compiled Express routes and the genuine Firebase Admin SDK connected to **Firebase Authentication Emulator** project `demo-localeats-r49`.
- The order/shop queries use a **purpose-built in-memory Supabase substitute**, not hosted database tables, service keys, a real merchant, bank, reward, paid collection or R4.6 ledgers. Its source data deliberately has separate Customer A and Customer B pickup orders and two merchant Firebase users. All order write gates remain disabled.
- `localeats-api/tests/rewards/r49/stagingLikeAuthFlow.test.mjs` verifies Customer A cannot read Customer B history or single order; customer responses omit private `create_intent_hash`; a revoked mock-project customer token receives 401 **before any order DB read**; a subsequently reauthenticated token can access only its own data; a disabled account receives 401; original merchant loses access after owner transfer and the new current shop owner is correctly recognised, but write endpoints still return `PICKUP_WRITES_DISABLED` (503); simulated Firebase outage fails closed, simulated DB outage returns 503, and restored connection resumes correct reads without inventing persisted state.
- Concurrent/sequential local route timings are measured using `performance.now()` for each HTTP response. The code **does not set or claim a Production/staging SLO**, and performance here cannot predict Firebase Admin's real network revocation-check lookup latency. Local test accounts/tokens are never production valid.

## Open customer login and security gate — do not claim end-to-end sign-in recovery

1. **Two session sources need careful reconciliation:** `LocalEats-app/src/App.tsx` restores and reacts to **Supabase** auth sessions; `LocalEats-app/src/services/customerPickup.ts` gets a separate **Firebase** `auth.currentUser.getIdToken()` for pickup requests. A valid Supabase session does not prove the Firebase pickup token hasn't been revoked. The Account Switch UI clears some cache on Supabase UID changes, but UI-level multi-source sign-out and authenticated history restoration remain **unverified**.
2. **Current 401 experience:** Customer pickup `src/pickup/client.ts` correctly throws a 401 error, but `src/App.tsx` catches pickup-history refresh failures as generic errors, and `src/screens/OrderHistoryScreen.tsx` shows **Retry**. A dedicated **“Session expired — Sign in again”** action on Firebase-revoked 401 is **not established**. End-to-end browser verification and an owner-approved minimal UX/security recovery fix are still required. Keep original Home startup, ShopCard, menu, cart, Profile and purchase flow unchanged in this phase.
3. **Merchant shop rights:** The ordinary merchant order action rechecks current `shops.owner_id`, which the local simulator verifies. The current `loadMerchantOrder` query selects `id,owner_id`; it does **not itself prove participating Rewards shop approval status**. Real LocalPay financial entitlement therefore needs its own server-enforced, purchase-time approved/opted-in shop scope. A successful ordinary merchant-auth test is not proof of real Rewards merchant eligibility.
4. **Actual hosted staging NOT verified:** No isolated hosted Firebase credentials, a distinct Supabase staging DB, secure Firebase frontend configuration, authorised test merchants or private network/region metrics were established by this phase. The prior repo instructions require `VITE_FIREBASE_CONFIG_SOURCE=environment` and complete **staging** app config before any staging browser build. A Vercel Preview alone may share Production and must not be used for real writes without isolation evidence.
5. **No plausible user-facing SLO can be set from localhost:** Real Firebase Admin `verifyIdToken(token,true)` may require network lookups; South African cellular and international connectivity, token revocation propagation, browser cold start and shop order refresh must be measured in a genuinely isolated environment before determining latency targets, timeout/retry budgets or failure UI.
6. **No reward finance guarantee:** R500 Bronze pilot actual backing, server checkout frozen eligible kota evidence, separate customer one-time pickup challenge, merchant till cash/card proof, immutable dispute/refund history, financial-grade DB RLS, consent/merchant terms and South African legal/privacy and future LocalPay registration issues remain open. Gold R80 / Platinum R150 credit lots are future-only and unfunded.
